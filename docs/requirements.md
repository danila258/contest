# Платформа практических работ по программированию

## Технологический стек

- В интерфейсах студента и преподавателя предпочтительны готовые компоненты из всей экосистемы Gravity UI, включая UIKit и специализированные библиотеки для иконок, навигации, таблиц и редактирования Markdown. Составные элементы, например форму настройки предмета, следует собирать из компонентов библиотеки. Собственные элементы управления уместны, когда готовые компоненты не покрывают требуемое поведение.
- Текстовые поля для документации (описание предмета, критерии оценивания и приёма работ, FAQ, условия вопросов и задач) поддерживают ввод, сохранение и отображение Markdown. Для редактирования используется Markdown Editor из Gravity UI.
- Monaco Editor для редактирования исходного кода на C++ в браузере.
- Vite для локальной разработки обоих интерфейсов.
- FastAPI для серверного API.
- PostgreSQL для хранения данных.
- Docker для запуска сервиса.

## Выбор из справочников

Если пользователь выбирает несколько значений из списка, который может вырасти, используйте выпадающий список Gravity UI с поиском и множественным выбором. Это правило применяется, например, к группам, студентам и преподавателям с доступом к предмету. Поиск работает по части названия или имени без учёта регистра. При смене запроса ранее выбранные значения сохраняются.

## Банк задач и тестов

- Предмет задаёт блок курса (например, МИСП, ПЗРЛ или РПО). Практические работы принадлежат предметам. Задачи и тесты хранятся в общем банке и могут входить в работы любых предметов.
- В карточке предмета преподаватель может выбрать «Копировать предмет», настроить учебный год, семестр и доступ и сохранить копию. У копии отдельные работы с собственными идентификаторами и сроками, сдвинутыми на разницу учебных лет. Начатые попытки, черновики и результаты остаются в исходном предмете.
- Каждая практическая работа привязана к одному предмету. Экран работы показывает этот предмет в формате «Алгоритмы · Семестр 1 · 2025/2026». Изменение сроков работы в копии предмета не меняет сроки исходной работы.
- В открытой практической работе преподаватель может выбрать «Копировать работу», изменить название, темы для подготовки, сроки и правила прохождения. В том же предмете создаётся отдельная работа с тем же порядком заданий и ссылками на те же задачи и тесты банка. При повторном копировании этой работы число материалов банка остаётся прежним. У копии своя статистика и свои попытки. Отмена оставляет работу и банк без изменений.
- Копия работы хранит ссылку на задачу по её ID. До начала работы изменения задачи в банке видны в её копии. При первом старте состав и условия фиксируются для прохождения. Копия использует те же тесты банка.
- Преподаватель видит общий банк с поиском и фильтром по предмету связанной работы. При выборе любого из предметов, в которых используется материал, он виден один раз. Список отсортирован по первому предмету в алфавитном порядке, затем по названию материала. Материалы без работ находятся в конце общего списка. Под названием задачи или теста предмет не выводится. При составлении работы можно выбрать материалы банка или создать новые. При сохранении работы все новые задачи и тесты автоматически добавляются в банк. Порядок заданий задаётся в каждой работе отдельно.
- При открытии задачи или теста перед содержимым показываются доступные пользователю практические работы, к которым прикреплён этот материал. При открытии существующей задачи или теста выбор предмета скрыт. Одноимённые работы можно различить по предмету, семестру и учебному году. Для материала без привязок показывается пустое состояние.
- В общем банке есть отдельный раздел теоретических вопросов. Вопрос может существовать самостоятельно или относиться к выбранным задачам банка.
- Преподаватель может импортировать предметы, практические работы, задачи и теоретические вопросы из JSON. Для каждого раздела доступен шаблон с английским описанием формата в первом поле `_comment`. Импорт поддерживает поля форм создания, связи по идентификаторам, вложенные тесты и задачи. Ошибка в одном элементе отменяет загрузку всего файла. Форматы доступны также для импорта из командной строки.
- Сценарий проверки: создать задачу и тест в работе одного предмета. После сохранения и перезагрузки найти оба материала в банке и добавить их в работу другого предмета. В банке каждый материал представлен один раз. Создать копию курса на следующий учебный год: в копии доступны те же задачи, их число в банке осталось прежним, сроки работ сдвинулись на год. Импорт файла с ошибкой оставляет банк без изменений.

## Аутентификация

1. У сайта должен быть вход по логину и паролю

2. Студенты и преподаватели используют одно и тоже окно для входа

## Требования для преподавателя

1. Можно создать новый предмет

   1. В настройках предмета можно настоить: название, доступ студентов по группе или индивидуально по ID студента (выбор с поиском по ФИО), доступ преподавателям, описание с критериями оценивания для студентов, FAQ для студентов, описание критериев приема работ для преподавателей

      Преподаватель выбирает цвет обложки и иконку из Gravity UI при создании и редактировании предмета. Предпросмотр и карточки предмета для обеих ролей показывают выбранное оформление.

      Для предмета указываются номер семестра от 1 до 12 и учебный год в формате «2026/2027». При создании доступны текущий учебный год и три следующих. Ранее сохранённый год за пределами этого диапазона сохраняется при редактировании, пока преподаватель сам его не изменит. Осень 2026 года и весна 2027 года относятся к одному учебному году 2026/2027. Весна длится с 5 февраля по 31 августа включительно, осень — с 1 сентября по 4 февраля следующего года включительно. На вкладке «Обзор» отображаются доступные предметы текущего учебного года, их работы и сроки: осенью — только нечётных семестров, весной — только чётных. На вкладке «Предметы» доступны предметы всех семестров. Поиск по части названия без учёта регистра сочетается с фильтрами по учебному году и номеру семестра. Если два предмета называются одинаково, поиск показывает обе карточки, а выбор года оставляет карточки соответствующего года. Если в этом году есть одноимённые предметы разных семестров, выбор семестра оставляет только соответствующую карточку. В фильтре предметов на вкладках «Практические работы» и «Банк задач и тестов» каждый вариант содержит название, семестр и учебный год, например «Алгоритмы · Семестр 1 · 2025/2026».

      У обеих ролей обзор показывает работы текущего семестра с момента открытия доступа до срока сдачи, ближайшие сроки идут первыми. Если у предмета есть будущая, открытая и просроченная работы, в таблицу обзора попадает только открытая. Полный список доступен в разделе «Практические работы» с учётом роли.

      На обзоре преподаватель видит открытые работы до срока сдачи. В предмете и в разделе «Практические работы» ему доступны также будущие и завершённые работы. До открытия работа показывает преподавателю предпросмотр заданий, с момента открытия — таблицу студентов с доступом, их статусов, зачтённых заданий и завершённых попыток. После дедлайна таблица остаётся доступной. Таблица преподавателя содержит столбцы «Название» и «Сдать до». Статусы выполнения и фильтр по ним доступны студенту. У студента «Доступна» означает, что можно приступить, а «В работе» — что он уже начал выполнение. Подтверждение начала переводит доступную работу студента в статус «В работе».

   2. Каждый предмет состоит из практических работ

   3. При открытии предмета появляется список практических работ из которого он состоит

Каждая практическая работа состоит из тестов и задач на програмирование с текстовым редактором

1. В практическую работу можно добавить любое количество тестов и задач на програмирование

Преподаватель может открыть созданную или импортированную работу и изменить её название, сроки, настройки прохождения, состав и порядок заданий в том числе после подтверждённого старта студента. Студент завершает начатое прохождение по сохранённой версии, а при новом старте другого студента используется обновлённая версия. Пока форма редактирования открыта, студент видит условия, а начало прохождения заблокировано. Сохранение, отмена или закрытие вкладки освобождают работу. Сохранение обновляет ту же работу. Отмена возвращает к сохранённой версии.

Сценарий проверки: студент открывает условия. Преподаватель открывает редактирование той же работы в другой вкладке. Старт становится недоступен. После сохранения студент видит обновлённые условия и подтверждает начало. Преподаватель видит начало работы в статистике и может изменить задания. Студент продолжает по первоначальным условиям, а сохранённые попытки учитываются по заданиям его версии.

2. В практической работе можно менять порядок тестов и задач на программирование. Если включена зависимость заданий, порядок отображения задаёт последовательность их выполнения: сначала первое задание, затем второе и так далее

3. В практической работе можно настроить название, сроки открытия доступа и срок сдачи, а также требование подтверждения выполнения преподавателем. Сдать работу нужно до указанного момента, в том числе если попытка уже начата. При наличии таймера время выполнения заканчивается по более раннему из двух сроков. Например, если до сдачи осталась минута, на выполнение доступна только эта минута.

   После названия преподаватель может заполнить необязательное поле «Темы для подготовки» в Markdown. После сохранения студент видит форматированный текст в условиях и при прохождении, преподаватель — при просмотре работы. Темы расположены после блока со сроками и условиями прохождения, перед заданиями. При повторном редактировании открывается исходный Markdown. Если поле пусто, раздел «Темы для подготовки» скрыт.

   В новой работе по умолчанию включены последовательное открытие заданий и подтверждение зачёта преподавателем.

   В форме создания обе даты показываются в формате ДД.ММ.ГГГГ и выбираются в пределах учебного года предмета (с 1 сентября по 31 августа включительно). Время показывается в формате ЧЧ:ММ. По умолчанию открытие — в 00:01, дедлайн — в 23:59.

4. Зависимости тестов и задач на программирование допускаются только в виде одной линейной цепочки в порядке отображения заданий. Следующее задание открывается после успешной автоматической проверки предыдущего: для теста достигнут порог правильных ответов, для задачи пройдены проверочные тесты и обязательные проверки. Подтверждение преподавателя для открытия следующего задания не требуется. Ветвления и циклы не допускаются

5. Для зачёта практической работы необходимо успешно выполнить все входящие в неё тесты и задачи. Для каждого теста и каждой задачи учитывается последняя завершённая попытка, а не лучшая. Если требуется подтверждение преподавателя, окончательный зачёт выставляет преподаватель; иначе работа засчитывается автоматически

Каждый тест состоит из вопросов

1. В тесте можно настроить название

2. В тесте можно настроить время студента на решение: сразу для всего теста или отдельно для каждого вопроса. Если разрешено возвращаться к предыдущим вопросам, таймер устанавливается только на весь тест. Таймеры отдельных вопросов доступны только при запрете возвращения

3. В тесте можно настроить возможность возвращения к предыдущему вопросу

4. По умолчанию в новом тесте перемешивание вариантов ответа включено, а возврат к предыдущим вопросам выключен. Преподаватель может изменить обе настройки. Студент видит правило возврата к вопросам. Настройка перемешивания видна только преподавателю.

5. В тесте можно настроить доступное количество попыток прохождения

6. В тесте можно настроить пороговое количество правильных ответов для успешной попытки

7. При запуске теста фиксируются переключение между вкладками и окнами, а также вставка кода. Они отображаются в отдельном окне

8. Каждый вопрос состоит условия вопроса и ответов на него

   1. Условие вопроса пишется в формате markdown с поддержкой математических формул

   2. Ответ можно пометить как правильный, но минимум 1 должен быть помечен

9. Для задачи по программированию преподаватель задаёт условие и начальный код, затем выбирает способ проверки: «Сравнение STDOUT», «Unit-тесты» или «Без тестов». В режиме «Без тестов» сохраняется пустой список проверочных тестов. Форматирование, статический и динамический анализ настраиваются отдельно.

   1. У задачи можно включить лимит времени студента на решение. Этот лимит не является ограничением времени выполнения программы

   2. Условие задачи пишется в формате markdown с поддержкой математических формул

   3. Студент редактирует исходные файлы в Monaco Editor с подсветкой синтаксиса C++ и нумерацией строк. При использовании unit-тестов студент может редактировать `main.cpp`, `task_name.cpp` и `task_name.h`. В `main.cpp` студент пишет собственную логику для самостоятельных запусков. При проверке через STDOUT используется один редактируемый файл `main.cpp`.

   4. Преподаватель может загрузить эталонное решение для проверки тестов

   5. Можно включить проверку форматирования, статический и динамический анализ кода. Преподаватель настраивает критичность ошибок этих проверок: какие ошибки блокируют зачёт задачи, а какие отображаются только как замечания

   По умолчанию нарушения форматирования блокируют зачёт, а результаты статического и динамического анализа выводятся как замечания.

   6. По умолчанию логи тестов скрыты от студента. Преподаватель может включить их показ.

   7. При запуске практической работы фиксируются переключение между вкладками и окнами, а также вставка кода. Для этих событий предусмотрен отдельный просмотр.

10. Доступен просмотр прогресса студентов для каждой практической работы

    1. Преподаватель может посмотреть отдельные попытки студента

    2. Преподаватель может посмотреть варианты ответов на тест у студента

    3. Преподаватель может посмотреть на код студента в решении задачи по програмированию

    4. Преподаватель может узнать длительность выполнения каждого теста и задачи по програмированию

    5. Преподаватель может оставить комментарий к практической работе и, если требуется ручное подтверждение, установить статус «зачтено» или «на доработке». После успешного выполнения всех заданий работа, требующая подтверждения, получает статус «ожидает проверки». Студент видит статус работы и комментарий преподавателя

    6. Преподаватель может дать студенту дополнительную попытку для отдельного теста или отдельной задачи по программированию. Дополнительная попытка не выдаётся на всю практическую работу целиком

## Требования для студентов

1. При первом открытии практической работы студент видит срок сдачи, время, число попыток и условия каждого задания. Вопросы и условия задач открываются после кнопки «Начать работу» и отдельного подтверждения. Отмена оставляет студента на экране условий. При возобновлении начатой работы повторное подтверждение не требуется. Перед началом теста показываются его условия: доступное время, возможность вернуться к предыдущему вопросу и т.д.

2. Перед началом выполнения задачи по программированию студенту показываются условия прохождения, включая лимит времени на решение, если он установлен

3. При наличии лимита времени на решение показывается не отвлекающий таймер с возможностью скрыть и показать его обратно. Таймер определяется сервером и не сбрасывается при перезагрузке страницы или закрытии вкладки

4. При выполнении задачи по программированию доступны кнопки «Запустить» и «Отправить на проверку». «Запустить» выполняет программу с main.cpp на введённых студентом данных и не влияет на зачёт. «Отправить на проверку» запускает закрытые тесты и настроенные проверки, создавая отдельную неизменяемую попытку с копией исходников и результатами проверки. Последующее редактирование кода не меняет отправленную попытку

5. При выполнении задания по програмированию должна быть возможность задать входные данные для main.cpp

6. Лог неудачного запуска задачи по программированию показывается под редактором с решением, там может быть лог компиляции, тестов (если преподаватель разрешил в настройках задания), форматера, динамического или статического анализа, а также STDOUT и STDERR

7. Должна быть возможность скачать лог падения

8. У практических работ должен отображаться дедлайн

9. У предметов должен отображаться ближайший дедлайн

10. Код и ответы сохраняются автоматически. Студент видит состояние сохранения. После перезагрузки страницы восстанавливается текущая попытка с сохранёнными кодом и ответами.

11. По истечении времени на решение автоматически отправляется последняя сохранённая на сервере версия кода или ответов, а редактирование этой попытки прекращается. При таймере на отдельный вопрос фиксируется последний сохранённый ответ на этот вопрос.

## Последующие доработки

Следующие замечания оставлены для отдельного согласования и не входят в утверждённые правила выше.

1. Определить последствия новой неудачной попытки после успешной: блокируются ли уже открытые задания цепочки, сохраняются ли результаты последующих заданий и как меняется ранее выставленный зачёт работы.

2. Уточнить доработку после комментария преподавателя: какие задания можно пересдавать, какие попытки и сроки предоставляются, когда работа снова получает статус «ожидает проверки».

3. Определить возможность выдачи дополнительной попытки после дедлайна, индивидуального продления доступа и разных сроков для групп.

4. Разделить сведения обычного запуска и закрытой проверки. Определить, какие логи, STDOUT, STDERR и сообщения анализаторов доступны студенту, чтобы не раскрывать скрытые тестовые данные. Скачивание должно учитывать те же ограничения, что и просмотр.

5. Описать среду проверки: стандарт C++, компилятор, параметры сборки, библиотеки, форматер и настройки анализаторов. Определить сравнение вывода с учётом пробелов, переводов строк и погрешности чисел; для unit-тестов — интерфейс решения, подключение проверок и отделение неизменяемых проверочных файлов от редактируемых файлов студента.

6. Описать технические ограничения каждого запуска независимо от учебного таймера: время компиляции и выполнения, память, процессы, объём вывода и файлов. Предусмотреть изоляцию от сервера и чужих решений, запрет сетевого доступа по умолчанию и остановку запуска.

7. Описать очередь проверки и статусы «в очереди», «компилируется», «проверяется», «завершено». Предусмотреть, что технический сбой проверяющего сервера не считается неправильным решением и не расходует попытку. Принятые сервером вовремя решения должны проверяться и после дедлайна.

8. Уточнить начало и подсчёт попыток задачи, лимит отправок на проверку и связь нескольких отправок с общим временем на решение. Определить момент запуска таймера и измерение длительности выполнения, включая очередь проверки и перерывы.

9. Описать создание пользователей и групп, назначение преподавателей и восстановление паролей. Разграничить права преподавателей на просмотр, проверку, редактирование и управление доступом. Ограничить доступ студентов собственными решениями и разрешёнными материалами.

10. Описать версии опубликованных условий и проверок, хранение прежних результатов и явную перепроверку после исправления тестов. Сохранять сведения о том, какая версия использовалась для каждой попытки.

11. Добавить предпросмотр глазами студента, экспорт ведомости и массовое скачивание решений.

12. Рассмотреть комментарии к конкретной попытке, историю изменений оценок и настроек, проверку сходства решений для последующего ручного рассмотрения, черновики, публикацию и архивирование работ.

13. Зафиксировать условия эксплуатации: число одновременно работающих студентов, число параллельных проверок, поддерживаемые браузеры, резервное копирование и восстановление данных.
