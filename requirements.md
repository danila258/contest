# Платформа практических работ по программированию

## Технологический стек

- Gravity UI для интерфейсов студента и преподавателя.
- Vite для локальной разработки обоих интерфейсов.
- FastAPI для серверного API.
- PostgreSQL для хранения данных.
- Docker для запуска сервиса.

## Аутентификация

1. У сайта должен быть вход по логину и паролю

2. Студенты и преподаватели используют одно и тоже окно для входа

## Требования для преподавателя

1. Можно создать новый предмет

   1. В настройках предмета можно настоить: название, доступ студентов по группе, доступ преподавателям, описание с критериями оценивания для студентов, FAQ для студентов, описание критериев приема работ для преподавателей

   2. Каждый предмет состоит из практических работ

   3. При открытии предмета появляется список практических работ из которого он состоит

Каждая практическая работа состоит из тестов и задач на програмирование с текстовым редактором

1. В практическую работу можно добавить любое количество тестов и задач на програмирование

2. В практической работе можно менять порядок тестов и задач на программирование. Если включена зависимость заданий, порядок отображения задаёт последовательность их выполнения: сначала первое задание, затем второе и так далее

3. В практической работе можно настроить название, сроки открытия доступа и дедлайн начала попыток, а также требование подтверждения выполнения преподавателем. Начать попытку можно в любой момент до дедлайна, в том числе за минуту до него. Наступление дедлайна не прерывает уже начатую попытку: студент может завершить её в пределах установленного времени на решение

4. Зависимости тестов и задач на программирование допускаются только в виде одной линейной цепочки в порядке отображения заданий. Следующее задание открывается после успешной автоматической проверки предыдущего: для теста достигнут порог правильных ответов, для задачи пройдены проверочные тесты и обязательные проверки. Подтверждение преподавателя для открытия следующего задания не требуется. Ветвления и циклы не допускаются

5. Для зачёта практической работы необходимо успешно выполнить все входящие в неё тесты и задачи. Для каждого теста и каждой задачи учитывается последняя завершённая попытка, а не лучшая. Если требуется подтверждение преподавателя, окончательный зачёт выставляет преподаватель; иначе работа засчитывается автоматически

Каждый тест состоит из вопросов

1. В тесте можно настроить название

2. В тесте можно настроить время студента на решение: сразу для всего теста или отдельно для каждого вопроса. Если разрешено возвращаться к предыдущим вопросам, таймер устанавливается только на весь тест. Таймеры отдельных вопросов доступны только при запрете возвращения

3. В тесте можно настроить возможность возвращения к предыдущему вопросу

4. В тесте можно настроить перемешивание вариантов ответа

5. В тесте можно настроить доступное количество попыток прохождения

6. В тесте можно настроить пороговое количество правильных ответов для успешной попытки

7. При запуске теста фиксируются переключение между вкладками и окнами, а также вставка кода. Они отображаются в отдельном окне

8. Каждый вопрос состоит условия вопроса и ответов на него

   1. Условие вопроса пишется в формате markdown с поддержкой математических формул

   2. Ответ можно пометить как правильный, но минимум 1 должен быть помечен

9. Каждая задача по програмированию состоит из условия задачи, начального исходного кода, тестов, включения проверки форматирования, включение статического и динамеческого анализа

   1. У задачи можно включить лимит времени студента на решение. Этот лимит не является ограничением времени выполнения программы

   2. Условие задачи пишется в формате markdown с поддержкой математических формул

   3. При использовании unit-тестов студент может редактировать main.cpp, task_name.cpp и task_name.h. В main.cpp студент пишет собственную логику для самостоятельных запусков. При проверке через STDOUT используется один редактируемый main.cpp

   4. Преподаватель может загрузить эталонное решение для проверки тестов

   5. Можно включить проверку форматирования, статический и динамический анализ кода. Преподаватель настраивает критичность ошибок этих проверок: какие ошибки блокируют зачёт задачи, а какие отображаются только как замечания

   6. Можно включить доступ к логам запусков тестов

   7. При запуске практической работы фиксируются переключение между вкладками и окнами, а также вставка кода. Для этих событий предусмотрен отдельный просмотр.

10. Доступен просмотр прогресса студентов для каждой практической работы

    1. Преподаватель может посмотреть отдельные попытки студента

    2. Преподаватель может посмотреть варианты ответов на тест у студента

    3. Преподаватель может посмотреть на код студента в решении задачи по програмированию

    4. Преподаватель может узнать длительность выполнения каждого теста и задачи по програмированию

    5. Преподаватель может оставить комментарий к практической работе и, если требуется ручное подтверждение, установить статус «зачтено» или «на доработке». После успешного выполнения всех заданий работа, требующая подтверждения, получает статус «ожидает проверки». Студент видит статус работы и комментарий преподавателя

    6. Преподаватель может дать студенту дополнительную попытку для отдельного теста или отдельной задачи по программированию. Дополнительная попытка не выдаётся на всю практическую работу целиком

## Требования для студентов

1. Перед началом теста показываются его условия: доступное время, возможность вернуться к предыдущему вопросу и т.д.

2. Перед началом выполнения задачи по программированию студенту показываются условия прохождения, включая лимит времени на решение, если он установлен

3. При наличии лимита времени на решение показывается не отвлекающий таймер с возможностью скрыть и показать его обратно. Таймер определяется сервером и не сбрасывается при перезагрузке страницы или закрытии вкладки

4. При выполнении задачи по программированию доступны кнопки «Запустить» и «Отправить на проверку». «Запустить» выполняет программу с main.cpp на введённых студентом данных и не влияет на зачёт. «Отправить на проверку» запускает закрытые тесты и настроенные проверки, создавая отдельную неизменяемую попытку с копией исходников и результатами проверки. Последующее редактирование кода не меняет отправленную попытку

5. При выполнении задания по програмированию должна быть возможность задать входные данные для main.cpp

6. Лог неудачного запуска задачи по программированию показывается под редактором с решением, там может быть лог компиляции, тестов (если преподаватель разрешил в настройках задания), форматера, динамического или статического анализа, а также STDOUT и STDERR

7. Должна быть возможность скачать лог падения

8. У практических работ должен отображаться дедлайн

9. У предметов должен отображаться ближайший дедлайн

10. Код и ответы сохраняются автоматически. Студент видит состояние сохранения. После перезагрузки страницы восстанавливается текущая попытка с сохранёнными кодом и ответами.

11. По истечении времени на решение автоматически отправляется последняя сохранённая на сервере версия кода или ответов, а редактирование этой попытки прекращается. При таймере на отдельный вопрос фиксируется последний сохранённый ответ на этот вопрос.

## Последующие доработки

Следующие замечания оставлены для отдельного согласования и не входят в утверждённые правила выше.

1. Определить последствия новой неудачной попытки после успешной: блокируются ли уже открытые задания цепочки, сохраняются ли результаты последующих заданий и как меняется ранее выставленный зачёт работы. Определить также правила изменения порядка заданий после начала прохождения.

2. Уточнить доработку после комментария преподавателя: какие задания можно пересдавать, какие попытки и сроки предоставляются, когда работа снова получает статус «ожидает проверки».

3. Определить возможность выдачи дополнительной попытки после дедлайна, индивидуального продления доступа и разных сроков для групп. Установить срок завершения начатой до дедлайна попытки, если у неё нет таймера.

4. Разделить сведения обычного запуска и закрытой проверки. Определить, какие логи, STDOUT, STDERR и сообщения анализаторов доступны студенту, чтобы не раскрывать скрытые тестовые данные. Скачивание должно учитывать те же ограничения, что и просмотр.

5. Описать среду проверки: стандарт C++, компилятор, параметры сборки, библиотеки, форматер и настройки анализаторов. Определить сравнение вывода с учётом пробелов, переводов строк и погрешности чисел; для unit-тестов — интерфейс решения, подключение проверок и отделение неизменяемых проверочных файлов от редактируемых файлов студента.

6. Описать технические ограничения каждого запуска независимо от учебного таймера: время компиляции и выполнения, память, процессы, объём вывода и файлов. Предусмотреть изоляцию от сервера и чужих решений, запрет сетевого доступа по умолчанию и остановку запуска.

7. Описать очередь проверки и статусы «в очереди», «компилируется», «проверяется», «завершено». Предусмотреть, что технический сбой проверяющего сервера не считается неправильным решением и не расходует попытку. Принятые сервером вовремя решения должны проверяться и после дедлайна.

8. Уточнить начало и подсчёт попыток задачи, лимит отправок на проверку и связь нескольких отправок с общим временем на решение. Определить момент запуска таймера и измерение длительности выполнения, включая очередь проверки и перерывы.

9. Описать создание пользователей и групп, назначение преподавателей и восстановление паролей. Разграничить права преподавателей на просмотр, проверку, редактирование и управление доступом. Ограничить доступ студентов собственными решениями и разрешёнными материалами.

10. Описать версии опубликованных условий и проверок, хранение прежних результатов и явную перепроверку после исправления тестов. Сохранять сведения о том, какая версия использовалась для каждой попытки.

11. Добавить копирование предметов и работ на следующий семестр, предпросмотр глазами студента, экспорт ведомости и массовое скачивание решений.

12. Рассмотреть комментарии к конкретной попытке, историю изменений оценок и настроек, проверку сходства решений для последующего ручного рассмотрения, черновики, публикацию и архивирование работ.

13. Зафиксировать условия эксплуатации: число одновременно работающих студентов, число параллельных проверок, поддерживаемые браузеры, резервное копирование и восстановление данных.
